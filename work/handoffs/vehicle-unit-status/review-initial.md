### Findings

1. **`app/dashboards/VehicleUnitStatusDashboard.tsx:180`** — `checkedAt` adds a manual `+7h` (`BANGKOK_UTC_OFFSET`-equivalent) shift to `lastUpdated` before passing it to `DashboardShell`'s `lastUpdated` prop, with the comment "convert the fetch instant to Bangkok digits." I checked the sibling `AlchemUnitStatusDashboard.tsx:331`, which passes `lastUpdated` straight through, unshifted. `DashboardShell` formats `lastUpdated` with `formatDateTimeGB` (`timeZone: 'UTC'` getters, `dateFormat.ts:3-12`), so:
   - Alchem's "Last checked" badge shows the raw UTC clock reading of the fetch instant.
   - Vehicle's "Last checked" badge shows that same instant shifted 7h forward.
   For roughly-simultaneous fetches, these two templates will display "Last checked" times that differ by 7 hours in the shared header component. Vehicle's version is arguably the *more correct* one relative to the project's own Bangkok-as-UTC convention, but it's a new, template-local deviation from how every other unit-status dashboard renders the same shell field today. Worth an explicit decision (fix Alchem too, or document why Vehicle alone gets the shift) rather than shipping a silent inconsistency — this is a "preservation of existing templates" concern since it changes the *meaning* of a shared UI field per-template. Not a data-isolation or security issue.

2. **`app/dashboards/vehicleUnitStatusData.ts:66-69`** — Fleet scoping is evaluated per row (`if (fleet.trim() && normalizedScope.size > 0 && !normalizedScope.has(...)) continue;`). A row with a *blank* `Fleet` cell always bypasses scoping, even when other rows in the same fetched tab do carry a `Fleet` value and a narrow scope is configured. This is deliberate and covered by tests (`vehicleUnitStatusData.test.ts:33-46`, the "accepting absent Fleet" case) and matches `docs/METRICS.md:126-131`'s "sheets without Fleet use the Vehicle company subset." However, the doc phrasing reads as a whole-sheet condition ("If an explicit Fleet field is present…"), while the code implements it row-by-row. On a mixed sheet (some rows tagged with a Fleet, others still blank), a dashboard scoped to one narrow fleet would still show the blank-Fleet rows alongside its own fleet's rows — a soft fleet-isolation gap within the same company, not a cross-company leak (company membership via `username` is still a hard, well-tested boundary). Given the sheet currently has "one unit at inspection" per the handoff, this is low current impact, but confirm this row-level interpretation is the intended long-term contract before more fleets/units are onboarded onto this sheet.

3. **`app/dashboards/VehicleUnitStatusDashboard.tsx:173-177`** — `invalidSource` re-implements a *second*, differently-normalized alias check (`label.toLowerCase().replace(/[^a-z0-9]/g, '')` against `['vehicleno','vehiclenumber']`/`'username'`) that duplicates, but doesn't share, `VEHICLE_NO_ALIASES`/`findValue` aliasing in `vehicleUnitStatusData.ts:34-35`. Functionally harmless today (both cover the real header set), but it's a second place to remember to update if a vehicle-number/username header alias is ever added — the kind of copy-drift `dashboardDataUtils.ts:82-90`'s `ALERT_TIME_ALIASES` comment specifically warns about for other templates. Consider deriving `invalidSource`'s check from the same alias list, or exporting a small `hasRequiredVehicleColumns(columns)` helper from `vehicleUnitStatusData.ts` instead.

4. **`app/dashboards/VehicleUnitStatusDashboard.tsx:256`** — `isReportedValue(row.videoLoss)` gates whether `videoLoss` renders inside a `badgeWarning`-styled span. Since `isReportedValue` treats numeric `"0"` as "reported" (by design, per `isReportedValue`'s doc comment and its own test), a literal `"0"` in a `videoloss` cell would render as a warning-colored badge showing "0". If the source sheet ever legitimately uses `"0"` to mean "no loss" (as opposed to "channel 0"), this would visually overstate a problem. This is consistent with the "no fabricated source values" mandate (the code doesn't invent meaning for `"0"`), so I'm not calling it a bug, but flagging it as worth a one-line confirmation with whoever defined the sheet schema, since it's the one field in this template where "reported non-empty" and "styled as a warning" are conflated.
